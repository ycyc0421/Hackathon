# 跨境单证合规校验

同一票跨境货物通常涉及报关单、商业发票、装箱单、提单等多份单证。这些文件由不同主体分别填写，格式与语言不统一，人工交叉核对成本高，且单证之间的不一致往往在报关或放货环节才暴露，直接导致滞港、罚款或退运。

本项目读取一票货物的多份单证，抽取其中的关键字段，交叉比对文件之间的一致性问题，并依据目的国规则提示证书缺失或编码归类风险。系统不判断哪份文件正确，只定位矛盾所在并给出可追溯的依据。

---

## 能力范围

| 环节 | 说明 |
|---|---|
| 单证解析 | 解析 PDF、图片格式的单证，输出结构化字段 |
| 字段抽取 | 抽取 HS 编码、件数、重量、金额等关键字段，并归一为可比较的值 |
| 交叉比对 | 在同一票货物的多份单证之间比对相同字段，标记不一致项 |
| 合规提示 | 依据目的国规则，提示证书缺失、编码归类等待复核事项 |
| 结果呈现 | 上传、差异、报告三个界面，以及模型评测看板 |

**系统不做的事**：不判定哪份文件的值正确，不给出海关归类的最终结论，不代替人工完成合规审查。所有风险提示均附规则编号与触发字段，未经规则校验的提示单独分组显示。

## 设计约束

以下三条约束贯穿数据结构与界面实现：

1. **状态必须可区分。** "本就不适用""应当存在但未抽取到""规则未覆盖"是三种不同情况，任何一种都不能与"校验通过"呈现为同一结果。
2. **失败必须显式。** 处理失败不得返回空结果，否则界面会将其渲染为"检查完成，没有问题"。
3. **不伪造数据。** 缺失的可信度、未运行的评测、未提供的定位信息一律如实留空，不使用默认值填充。

## 数据契约

前后端之间的数据格式以 [`docs/schema/check-task.schema.json`](docs/schema/check-task.schema.json) 为唯一事实来源，[`docs/数据契约.md`](docs/数据契约.md) 是其可读版本，两者内容一致。

```sh
npm install
npm run validate
```

校验分两个层面：结构（字段名、类型、枚举取值、必填项）与自洽（`summary` 中的计数须与数组实际长度一致）。契约中还包含若干跨字段约束，用于防止静默错误，例如要求 `NOT_CHECKED` 状态必须给出未校验原因、`CONFLICT` 状态至少包含两个不同值。

后端就绪后，将其真实返回交给校验脚本即可判定是否符合契约。

## 前端

```sh
cd web
npm install
npm run dev      # 开发服务器
npm run build    # 产出 dist/
```

| 页面 | 职责 |
|---|---|
| 上传 | 选择同一票货物的多份单证，创建检查任务，查看逐文件处理状态 |
| 差异 | 展示各字段在文件间的比对结果，定位到具体文件与值 |
| 报告 | 本次检查的汇总、待处理条目与风险提示 |
| 评测 | 模型跑分结果与错误分类 |

开发期默认读取本地示例数据。切换至真实后端只需修改 `web/src/api/config.js` 中的 `USE_MOCK`。

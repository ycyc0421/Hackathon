# 跨境单证合规校验

> 一票跨境货物的多份单证，自动交叉比对——把"报关环节才发现对不上"提前到"提交前就看见"。

同一票货物往往涉及商业发票、装箱单、提单、报关单等多份单证。它们由不同主体分别填写、格式与语言不一，人工逐份核对成本高；而单证之间的矛盾（件数对不上、毛重不一致、HS 编码归类存疑）常常拖到报关或放货环节才暴露，直接导致滞港、罚款乃至退运。

本项目读取一票货物的多份单证，抽取关键字段，**交叉比对文件之间的一致性**，并依据目的国规则提示证书缺失或归类风险。系统不替人下结论——它只定位矛盾、给出可追溯的依据，把最终判断留给负责合规的人。

**在线 Demo**：https://hackathon-demo.ychome.net

线上默认使用内置示例数据；真实后端需单独运行，并配置 API 连接。

## 功能

| 能力 | 说明 |
|---|---|
| 单证解析 | 读取带文本层的 PDF；图片和扫描 PDF 需配置识别服务，无法识别时明确报错 |
| 字段抽取 | 抽取 HS 编码、件数、毛重、金额等关键字段，并归一为可比较的值 |
| 交叉比对 | 按整票或品名行核对字段，标记差异并关联来源文件与原始值；无法可靠对齐的行标记为未校验 |
| 合规提示 | 按目的国演示规则提示证书缺失、归类待复核等事项；规则尚未经正式核实，结果明确标注 |
| 结果呈现 | 上传 / 差异 / 报告三个工作界面，另附模型评测看板 |
| 后端接口 | 创建核验任务、轮询任务状态与结果；真实评测尚未运行时返回“尚未评测” |

**系统明确不做的事**：不判定哪份文件的值正确，不给出海关归类的最终结论，不代替人工完成合规审查。未经规则校验的提示会单独分组，与规则命中的提示区分开。

## 设计原则

三条约束贯穿数据结构与界面实现：

1. **状态必须可区分。** "本就不适用"（NOT_IN_DOC）、"应当存在却没抽到"（MISSING_IN_DOC）、"规则未覆盖"（NOT_CHECKED）是三种不同情况，**任何一种都不能被渲染成"校验通过"**。
2. **失败必须显式。** 处理失败绝不返回空结果——否则界面会把它显示成"检查完成，没有问题"。
3. **不伪造数据。** 缺失的可信度、未运行的评测、未提供的定位信息一律如实留空，不用默认值填充，也不为了页面好看而编一个数字。

## 快速开始

前端可独立运行，默认读取内置示例数据。以下命令均在仓库根目录执行：

```sh
npm ci
npm run validate
npm --prefix web ci
npm --prefix web run dev    # 开发服务器默认 http://localhost:5173
```

构建前端：

```sh
npm --prefix web run build  # 构建到 web/dist/
```

真实后端的启动方式、接口和验证命令见 [`backend/README.md`](backend/README.md)。本地联调时，先启动后端，再在另一个终端设置 `VITE_API_BASE` 并启动前端。例如在 Linux / macOS 上：

```sh
VITE_API_BASE=http://127.0.0.1:8000/api/v1 npm --prefix web run dev
```

在前端顶栏切换数据源，或通过 URL 参数 `?mock=0` 使用真实后端、`?mock=1` 使用示例数据。切换数据源无需修改代码；`VITE_API_BASE` 在前端启动或构建时读取，未设置时请求同源 `/api/v1`。

当前 [部署工作流](.github/workflows/deploy.yml) 只发布前端与 JS Worker，不部署 `backend/`。线上接入真实后端还需配置 [`worker/index.js`](worker/index.js) 中的 API 代理。

## 技术栈

- **前端**：Vue 3（`<script setup>`）+ Vite 6，自研设计系统（OKLCH 色彩、CSS 变量 token），无 UI 组件库 / 路由 / 状态管理依赖
- **后端**：Python 3.12+、FastAPI、Pydantic、pypdf；可配置多模态识别服务
- **边缘部署**：Cloudflare Workers + Assets 绑定，托管静态前端并预留 `/api/` 反向代理
- **契约校验**：JSON Schema + AJV，含结构与跨字段自洽两层校验

## 架构

```
浏览器 ──► Cloudflare Worker ──► web/dist 静态资源
                    └── /api/ 代理（待配置）──► FastAPI 后端

本地开发：Vite 前端 ──► FastAPI 后端

接口数据格式：docs/schema/check-task.schema.json
```

前端不直接 `fetch`，统一走 `web/src/api/index.js`；状态文案集中在 `web/src/api/labels.js`。请求层内置网络/5xx 指数退避重试、慢轮询提示，以及全局错误边界防止白屏。

## 数据契约

前后端之间的数据格式以 [`docs/schema/check-task.schema.json`](docs/schema/check-task.schema.json) 为**唯一事实来源**，[`docs/数据契约.md`](docs/数据契约.md) 是其可读版本，两者保持一致。

`npm run validate` 校验两个层面：

- **结构**：字段名、类型、枚举取值、必填项；
- **自洽**：`summary` 中的计数须与数组实际长度一致；并含跨字段约束以防静默错误（如 `NOT_CHECKED` 必须给出未校验原因、`CONFLICT` 至少包含两个不同值）。

后端自检脚本会调用本地应用接口，并用同一份 Schema 校验返回结果；运行方式见 [后端验证说明](backend/README.md#验证与样例)。

## 项目结构

```
├── backend/                单证核验后端（FastAPI）
│   ├── app/                读取、抽取、归一、行对齐、比对与规则提示
│   ├── samples/            合成单证样例
│   └── tools/              接口自检与回归脚本
├── docs/                   数据契约与项目文档
│   ├── 数据契约.md          契约的可读版本
│   ├── schema/             契约的 JSON Schema 与校验脚本
│   └── fixtures/           示例数据

│   └── src/
│       ├── api/            请求封装与状态文案

```

## 协作

本项目为团队协作开发：前端侧整理并提出契约与接口要求，数据侧与后端侧共同确认。变更契约前请先同步，避免前后端各按一套实现。

问题反馈与改动通过 Issue、PR 协作。提交前执行 `npm run validate` 和 `npm --prefix web run build`；接口变更需同步 Schema、示例数据与契约文档。设计系统规范见 [`web/DESIGN.md`](web/DESIGN.md)。

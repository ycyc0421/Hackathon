# 多品名 `items[]` 数据结构方案

更新时间：2026-10-10

本文只说明一票货包含多个品名时，如何使用 `items[]` 和 `item_id` 组织数据，供 C、D、F 对齐协议、数据库和差异页。

## 一、要解决的问题

一票货可能包含多种商品：

| 商品 | 发票数量 | 装箱单数量 |
|---|---:|---:|
| 陶瓷马克杯 | 2400 | 2500 |
| 玻璃水杯 | 800 | 800 |

如果只返回一组 `quantity` 值，系统无法知道哪些值属于同一种商品，也无法正确显示“马克杯数量冲突、玻璃水杯数量一致”。因此需要给每项商品一个任务内的身份，并让抽取字段和比对结果引用这个身份。

## 二、误解澄清

### `item_id` 不是商品类别

`item_id` 不是“陶瓷制品”这样的分类，也不是 HS 编码。HS 编码仍然单独存放在 `hs_code` 字段中。

### `item_id` 不是商品属性

商品描述、数量、重量、金额和 HS 编码是商品字段；`item_id` 只是把这些字段归到同一项商品下面的关联键。

### `item_id` 不是正确答案

系统不会因为一个商品有 `item_id` 就认定某份单证的数量或 HS 编码正确。不同文件中的值都要保留并由 F 比对，冲突时 `canonical_value` 仍为 `null`。

### `item_id` 只在当前任务内有效

`item_001` 只表示当前 `task_id` 中的第一项商品。另一票货可以重新使用 `item_001`，两者不是同一条永久商品记录。

### `line_no` 不是跨文件身份

`line_no` 只表示某份文件中的行号。发票第 1 行和装箱单第 1 行不一定是同一种商品，不能仅凭 `line_no` 跨文件匹配。

## 三、`items[]` 是什么

`items[]` 是当前检查任务中的商品目录，每个元素代表一项需要被抽取和比对的商品：

```json
{
  "items": [
    {
      "item_id": "item_001",
      "display_name": "陶瓷马克杯",
      "description": "CERAMIC MUG 350ML WHITE",
      "line_no": 1
    },
    {
      "item_id": "item_002",
      "display_name": "玻璃水杯",
      "description": "GLASS CUP 500ML",
      "line_no": 2
    }
  ]
}
```

`items[]` 只保存商品身份和展示信息，不放数量、重量或 HS 编码的“最终值”，因为这些值可能在单证之间冲突。

## 四、第一版单品名如何兼容

第一版每票只有一个品名，也返回同一套结构，只是数组长度为 1：

```json
{
  "items": [
    {
      "item_id": "item_001",
      "display_name": "陶瓷马克杯",
      "description": "CERAMIC MUG 350ML WHITE",
      "line_no": 1
    }
  ]
}
```

因此第一版可以只用单品名样例，后续增加第二个商品时只需增加数组元素，不必重做顶层 JSON 或比较接口。

## 五、抽取与比对如何引用商品

商品字段在 `extractions[].fields[]` 中增加 `item_id`：

```json
{
  "field_key": "quantity",
  "label": "数量",
  "item_id": "item_001",
  "line_no": 1,
  "raw_value": "2400 PCS",
  "normalized_value": 2400,
  "unit": "PCS",
  "status": "EXTRACTED"
}
```

比对结果的比较键是 `item_id + field_key`：

```json
{
  "comparison_id": "cmp_001",
  "item_id": "item_001",
  "field_key": "quantity",
  "label": "数量",
  "value_type": "NUMBER",
  "unit": "PCS",
  "status": "CONFLICT",
  "canonical_value": null,
  "severity": "ERROR",
  "values": [
    {"file_id": "f1", "file_name": "invoice.pdf", "raw_value": "2400 PCS", "normalized_value": 2400, "field_status": "EXTRACTED"},
    {"file_id": "f2", "file_name": "packing-list.pdf", "raw_value": "2500 PCS", "normalized_value": 2500, "field_status": "EXTRACTED"}
  ]
}
```

这只表示 `item_001` 的数量冲突，不表示 2400 或 2500 哪个正确。整票字段的结果使用 `item_id: null`，例如整票装运日期。

## 六、字段归属

商品级字段在单证按商品行提供时关联 `item_id`：

```text
description, hs_code, quantity, packages, gross_weight,
net_weight, volume, total_amount, currency
```

整票级字段通常使用 `item_id: null`：

```text
invoice_no, shipment_date, bill_of_lading_no, contract_no,
container_no, shipper, consignee, port_of_loading,
port_of_discharge, destination_country
```

`packages`、`gross_weight`、`net_weight`、`volume` 可能是商品行值，也可能是整票汇总值：按商品行提供就关联 `item_id`，只有整票总值就使用 `null`，不要把总值复制到每个商品。

## 七、三方职责

- **C**：保存商品目录、原始行号、商品描述和字段值，并维护 SQLite 关联。
- **F**：判断不同文件中的商品是否属于同一 `item_id`，按 `item_id + field_key` 生成比对结果；匹配失败时明确返回未检查或错误状态。
- **D**：按 `item_id` 分组显示差异，使用 `display_name` 展示商品名称；整票字段单独显示。

## 八、需要同步修改的文件

### `docs/schema/check-task.schema.json`

需要增加：

1. 顶层 `items` 数组和 `$defs/Item`；
2. `Field.item_id`、`Field.line_no`；
3. `Comparison.item_id`；
4. `ComparisonValue` 中用于追溯的 `item_id`（可选）；
5. `item_id` 在同一任务内唯一的约束。

建议的 `Item`：

```json
{
  "type": "object",
  "required": ["item_id", "display_name"],
  "additionalProperties": false,
  "properties": {
    "item_id": {"type": "string", "pattern": "^item_[a-zA-Z0-9_-]+$"},
    "display_name": {"type": "string"},
    "description": {"type": ["string", "null"]},
    "line_no": {"type": ["integer", "null"], "minimum": 1}
  }
}
```

暂不强制所有字段必须有 `item_id`，因为整票字段合法地使用 `null`。

### `docs/数据契约.md` 与 `docs/fixtures/`

补充 `items[]`、任务内 `item_id`、`item_id + field_key` 比较键和整票字段规则。现有单品名样例增加一个 `item_001`；之后再增加一个双品名样例，覆盖一致、冲突和缺失。

### `data/schema.sql`

增加商品表，并让字段表和比对表保存 `item_id`：

```sql
CREATE TABLE items (
    task_id TEXT NOT NULL,
    item_id TEXT NOT NULL,
    display_name TEXT NOT NULL,
    description TEXT,
    line_no INTEGER,
    PRIMARY KEY (task_id, item_id),
    FOREIGN KEY (task_id) REFERENCES tasks(task_id) ON DELETE CASCADE
);
```

以下表增加 `item_id`：

```text
extracted_fields
comparisons
comparison_values
```

数据库关联应带上 `task_id`，因为 `item_id` 只在当前任务内有效。

## 九、共同确认的问题

1. 是否采用顶层 `items[]`；
2. `item_id` 由 C、F 还是统一后端生成；
3. 商品匹配失败时返回哪种状态；
4. 汇总字段是否允许 `item_id = null`；
5. `line_no` 记录原始文件行号还是统一商品行号。

## 十、建议结论

采用 `items[]` 作为当前任务内的商品目录。`item_id` 只是商品关联键，不是类别、属性、HS 编码或正确答案。第一版按单品名交付，但也返回只有一个元素的 `items[]`；后续多品名时增加元素。商品字段和比对结果通过 `item_id` 关联，整票字段使用 `item_id = null`，比较键为 `item_id + field_key`。协议、Schema、示例数据、SQLite 和前端差异页按此方向同步。

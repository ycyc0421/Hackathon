# 演示与验证指南

## 选择数据源

- [真实后端模式](https://hackathon.ychome.net/?mock=0)：文件上传到服务器并实际处理。
- [示例模式](https://hackathon.ychome.net/?mock=1)：展示内置结果，不能用来证明 OCR 或后端已运行。

顶栏应明确显示当前模式。切换模式会刷新页面，不承接另一数据源的任务与本地文件状态。真实演示使用合成或已确认脱敏的资料。

## 推荐演示顺序

输入均来自 [backend/samples](../backend/samples/)。每次只上传同一目录、同一票货物、同一种测试格式的一组文件，不把 PNG 和相同内容 PDF 混在一次任务中。

| 输入 | 验证目的 | 应检查什么 |
|---|---|---|
| `01_us_consistent` 的 PDF，目的国 US | 值一致 | 任务完成、冲突计数为 0；不据此宣称整票合规 |
| `02_de_conflict` 的 PDF，目的国 DE | 差异展示 | 非零冲突，能追溯到各文件原值 |
| `04_de_multiitem` 的 PDF，目的国 DE | 多商品 | 商品分别显示，比对不把不同商品混在一起 |
| 06、07 号样例的 PDF，目的国 DE | 缺行或对齐不确定 | 对照该样例预期，无法核验时显示未核验而非一致 |
| `11_de_multiitem_mixed` 的三张 PNG，目的国 DE | 本地 OCR | 全部文件抽取成功、4 个商品、品名颜色冲突、校正证据与警告 |
| 11 号 PNG 封装的扫描 PDF | PDF 渲染＋OCR | 确认无文本层、所有文件走 OCR、商品完整；自动部署会生成并验证 |

其他样例目录和明确断言见[后端样例表](../backend/README.md#验证与样例)与[挑战金标预期](../backend/samples/challenge/金标预期.md)。上表不代替金标清单；尤其不要从某次输出反推“正确答案”。

## 页面检查清单

1. 上传页：文件名、格式、数量和目的国正确；同名文件、超限输入给出明确反馈。扫描预检测是启发式提示，不证明服务器不能识别。
2. 任务状态：上传、解析和终态共用同一视图；逐文件由排队进入解析及文件终态，已处理计数递增。`COMPLETED`、`PARTIAL`、`FAILED` 分开；失败文件的错误仍可见。
3. 差异页：按商品与字段检查来源值、原文、缺失、未识别及 `NOT_CHECKED`；低可信值即使比较一致也需提示复核。
4. 报告页：摘要计数与条目一致，规则提示保留“未经核实”说明，不给用户指定哪份文件正确。
5. 评测页：没有真实评测时显示“尚未评测”，不填默认分数。
6. 没有 `confidence`、`bbox` 或页码时不生成虚假信息；刷新后本地 File 对象可能丢失，不假设仍能打开原件。

前端扫描件提示存在已登记的旧文案；详见[项目现状](项目现状与计划.md)。前端轮询和发布探针的等待上限不同，页面超时不等于后台任务已停止。

## 本地验证命令

以下命令从仓库根目录执行。先按[后端安装说明](../backend/README.md#运行)准备并激活 Python 环境，再安装根目录与前端 npm 依赖。

```sh
npm ci
npm --prefix web ci
npm run validate
node --test tests/*.test.mjs
npm --prefix web run build
python backend/tools/test_compare.py
python backend/tools/test_review_regressions.py
python backend/tools/test_paddle_adapter.py
python backend/tools/selftest.py
python backend/tools/run_challenge.py
python -m unittest discover -s data -p 'test_*.py' -v
python -m unittest discover -s deploy -p 'test_*.py' -v
```

普通回归应在 `PADDLE_OCR_ENABLED=0` 且未配置 LLM 的独立环境执行，避免模型下载以及“识别通道未配置”的断言被改变；发布脚本会隔离相关配置。不要在生产共享任务目录运行这些测试。

真实 OCR 使用[独立 OCR 环境](../backend/README.md#本地-paddleocr可选)：

```sh
python backend/tools/run_ocr_probe.py 11_de_multiitem_mixed
```

该脚本自行启用 PaddleOCR，默认不传样例名时跑 09–11；它不是正式评测器。没有 GPU 也可使用当前 CPU 配置。

## 逐文件进度验收

本地后端配合 `VITE_PROXY_API=http://127.0.0.1:8000 npm --prefix web run dev`，在真实模式上传同票、文件名不同的 5–10 份单证。选择处理时间足以跨越轮询间隔的输入；文本 PDF 很快时，可能直接看到终态，不应人为补播进度。

同时观察 GET /api/v1/checks/{task_id}：documents 按上传顺序增长，当前文件 PARSING，结束后为 EXTRACTED、FAILED 或 UNSUPPORTED；每条 file_id 只出现一次。summary.document_count 等于已发布文件数。逐文件终态中的失败也计入“已处理”，但不能显示为成功。

最终文件顺序、任务状态、抽取与比对结果应与同输入的旧流水线一致。无需下载 OCR 模型即可用隔离测试中的受控解析等待验证中间态；等待仅用于测试，不写入生产代码。

## 保存结果与校验

`selftest.py` 把返回值写入 `backend/.out/`，挑战集写入 `backend/.out/challenge/`。这些目录不提交。

```sh
node backend/tools/validate_outputs.mjs backend/.out
node backend/tools/validate_outputs.mjs backend/.out/challenge
```

校验器要求目录中的任务结果符合当前 Schema；评测结果文件名为 `evaluation.json`。它还检查摘要计数、重复 ID 与文件/商品引用。

需要交接一轮验证时，记录：代码提交、数据集/样例版本、执行命令、模型与依赖版本、环境配置、输入格式、任务 ID、状态、预期与实际差异、耗时口径。只提交适合公开的合成输入和已审查的说明，不提交含敏感信息的原始结果。

## 回归、部署验证和正式评测的区别

| 类型 | 回答的问题 | 不能推出的结论 |
|---|---|---|
| 逻辑/契约回归 | 已知边界是否符合约定 | 真实文档识别准确率 |
| 模型/公网探针 | 当前版本是否能走通指定输入和整站链路 | 全格式覆盖或并发容量 |
| 正式评测 | 在固定金标集上按确定口径表现如何 | 未覆盖场景也可靠 |

正式评测须先确认字段抽取、冲突检测和风险提示的统计单位、分母、失败样本处理、规则真值及数据许可。当前不设未经讨论的达标阈值。

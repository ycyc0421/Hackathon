# PaddleOCR-VL-1.6 主模型部署与工程架构说明

本文档说明生产环境采用的 **PaddleOCR-VL-1.6** 版面理解与识别主模型架构、运行资源隔离策略及关键解析机制。

---

## 1. 模型版本与服务架构

生产服务器在 8 GiB 内存、4 核 CPU 环境下运行三层本地服务，统一受 `systemd --user` 的 `hackathon.slice` 资源配额管理：

| 服务单元 | 监听端口 | 职责说明 |
|---|---|---|
| `hackathon-backend.service` | `127.0.0.1:18000` | FastAPI 业务后端（任务调度、字段抽取、归一化、行对齐与交叉比对） |
| `hackathon-paddle-vl.service` | `127.0.0.1:18082` | PaddleOCR-VL 文档解析服务（版面区域检测 `PP-DocLayoutV3` 与表格/文本编排） |
| `hackathon-vl-rec.service` | `127.0.0.1:18083` | 基于 `llama.cpp`（`b11429`）的 `PaddleOCR-VL-1.6` 官方 GGUF 文本识别服务 |

- **固定版本与完整性校验**：[`deploy/prepare_vl_cpu.py`](../deploy/prepare_vl_cpu.py) 锁定模型仓库 revision（GGUF `511b0964...`、版面模型 `241f8bdf...`）与每个权重文件的 SHA-256 指纹。
- **确定性本地推理**：文本层 PDF 直接解析；图片与无文本层扫描 PDF 经 200 DPI 按页渲染后交由本地 `PaddleOCR-VL-1.6` 推理，不依赖外部商业大模型 API，识别失败时显式报错而不静默回退。

## 2. 并发控制、原件保护与字段还原机制

1. **原件落盘先行与中断安全**：
   - 上传请求到达后，先将全部原始文件字节与文档清单持久化至磁盘与 SQLite，再启动解析流水线。
   - 若服务在推理途中重启，所有未完成任务自动收尾为 `FAILED`（附 `TASK_INTERRUPTED`），已保存的原件仍可通过下载接口取回。
2. **有界队列与内存保护**：
   - 后端最多同时接纳 4 票运行或排队中的任务（2 个编排工作线程，模型推理单并发串行执行）；第 5 票并发请求直接返回 `HTTP 429 CHECK_QUEUE_FULL`。
   - 排队任务仅持有磁盘文件路径，扫描件 PDF 按页流式渲染，实测多票并发下总内存峰值控制在约 4.14 GiB（配额上限 8 GiB）。
3. **表格结构还原与严格降级**：
   - 适配器完整保留模型输出的页码、区域像素矩形（`bbox`）、HTML 表格网格（含 `colspan` / 空单元格）与原文片段。
   - 区分单证自身的编号（`document_no`）与商业发票引用号（`invoice_no`）；包装件数（`packages`）仅在原文具备明确箱数单位（`CTNS` / `CARTON` / `箱`）时归一为 `CARTON`，裸 `PKGS` 保留 `unit=null` 并提示人工复核。

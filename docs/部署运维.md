# 部署与运维手册

本文档说明生产环境（`https://hackathon.ychome.net`）的部署拓扑、目录结构、日常巡检、版本回退及故障排查流程。CI/CD 自动化发布机制详见 [CI/CD 工作流说明](../.github/workflows/README.md)。

---

## 1. 生产环境拓扑

```text
客户端浏览器 ──► Cloudflare HTTPS 代理 ──► 源站 Nginx
                                            ├─ /            ──► ~/app/current/web/dist（前端静态资源）
                                            └─ /api/v1/...  ──► 127.0.0.1:18000（FastAPI 后端服务）
                                                                  ├─ 127.0.0.1:18082（PaddleOCR-VL 文档服务）
                                                                  ├─ 127.0.0.1:18083（GGUF CPU 推理服务）
                                                                  └─ ~/app/shared/data（跨版本共享数据）
```

前端与后端同源部署，前端直接请求相对路径 `/api/v1`，无需配置跨域或外部 API 地址。

---

## 2. 服务器目录结构

```text
~/app/
├── current -> releases/<当前发布标识>   # 当前生效版本的原子软链接
├── releases/                          # 历次发布版本（含后端代码、web/dist、.venv 软链与 requirements.lock）
├── shared/
│   ├── backend.env                    # 服务端私有环境变量配置
│   ├── python-envs/                   # 按依赖指纹缓存的 Python 3.12 虚拟环境
│   ├── rule-sources/                  # 官方规则来源定时抓取快照与清单
│   └── data/                          # 跨版本持久化数据（tasks.sqlite3、上传原件、evaluation/ 评测档案）
└── venv/                              # 环境构建引导工具
```

## 3. 日常状态巡检

使用维护账户通过 SSH 登录服务器后，可执行以下命令检查服务健康度与资源水位：

```sh
# 查看当前生效版本
readlink -f ~/app/current

# 查看后端与模型服务状态及内存水位
systemctl --user status hackathon-backend --no-pager
systemctl --user show hackathon-backend -p MemoryCurrent -p MemoryPeak -p MemoryHigh -p MemoryMax -p CPUQuotaPerSecUSec

# 本机健康检查（返回 status 与 release_revision）
curl --fail --silent --show-error http://127.0.0.1:18000/health

# 查看最近服务日志
journalctl --user -u hackathon-backend -n 50 --no-pager
```

## 4. 版本发布与回退

### 自动发布与自动回退

合并至 `main` 并通过 CI 后，`deploy.yml` 会自动打包上传新版本、准备依赖环境、更新 `~/app/current` 并重启服务，随后立即从公网执行端到端探针（覆盖首页静态资源、文本 PDF 比对及真实扫描件 OCR）。若任一探针失败，发布脚本会自动停止新服务并恢复上一版本的软链接、依赖环境与服务配置。

### 手动回退

如需人工撤回当前线上版本，先确认 `~/app/current` 指向的当前发布标识，再执行回退命令：

```sh
python3 ~/app/current/deploy/backend.py <当前发布标识> --rollback
```

> **注意**：版本回退仅切换代码、前端静态资源与运行环境，**不会回滚 `~/app/shared/data` 中的任务记录与评测结果**。

## 5. 数据持久化与备份

- **任务与原件存储**：所有任务状态、抽取证据与人工修正审计保存在 `~/app/shared/data/tasks.sqlite3`，并在任务完成时同步导出兼容 JSON 快照。服务重启时会将未完成的任务标记为 `FAILED / TASK_INTERRUPTED`，原件保留可下载。
- **系统评测档案**：`~/app/shared/data/evaluation/` 保存 `latest.json` 与 `runs/` 历史批次，发版与回退均不删除。更新评测结果请使用 `evaluate_dataset.py --publish`，勿手工覆盖文件。
- **备份建议**：在无进行中任务的维护窗口内，对 `~/app/shared/data/` 进行整体冷备或使用 `sqlite3 .backup` 备份数据库，并记录对应的代码版本标识。

## 6. 资源配额与常见故障排查

后端 API（`18000`）、PaddleOCR-VL 文档服务（`18082`）与 GGUF 推理服务（`18083`）共享 `hackathon.slice`（总内存上限 8 GiB，CPU 配额 4 核）。模型推理采用单并发串行复用，API 最多同时接纳 4 票运行或排队任务，超出时返回 HTTP 429 `CHECK_QUEUE_FULL`。

| 故障现象 | 排查方法 |
|---|---|
| 页面可打开但上传后未调用后端 | 检查浏览器地址栏或 `localStorage` 是否处于示例模式（访问 `?mock=0` 切回真实后端） |
| 扫描件处理耗时较长 | CPU 环境下多页或高分辨率扫描件推理可能需要数分钟；前端轮询窗口最长支持 30 分钟，可通过日志观察推理进度 |
| 上传返回 HTTP 429 | 当前并发/排队任务已满 4 票上限，等待已有任务完成后重试 |
| 内存水位偏高或服务重启 | 使用 `systemctl --user show` 检查 `MemoryPeak` 与 `journalctl` 日志，确认是否有异常大图触发内存保护 |
| 本机 `/health` 正常但公网不可达 | 依次检查 Nginx 配置（`nginx -t`）、源站证书有效期及 Cloudflare 代理状态 |

# 部署与运维

适用基线：2026-10-12 main。发布机制和初始化前提见 [CI/CD 工作流](../.github/workflows/README.md)，本页说明日常检查、故障定位与数据边界。

## 当前拓扑

公开入口为 `https://hackathon.ychome.net`。Cloudflare 代理后由 Nginx 提供前端，并把 `/api/`、`/health`、`/docs`、`/openapi.json` 转发到本机 FastAPI。前端使用同源 `/api/v1`，生产构建不需要 VITE_API_BASE。

历史后端与演示子域名只作跳转，不能继续作为新接入地址。源站证书、Cloudflare 来源 IP 限制和 DNS 由管理员维护，不由 GitHub 发布脚本重建。当前区域 TLS 模式为 Full，不应写成已启用 Full (strict)。证书更新尚未纳入自动发布，需单独维护。

## 版本与配置

```text
~/app/
├── current -> releases/<发布标识>
├── releases/       每次发布的代码、web/dist、独立 .venv 与依赖记录
├── shared/
│   ├── backend.env 运行配置（私有）
│   └── data/       共享任务数据（私有）
└── venv/           安装新版本依赖的引导环境
```

GitHub production 环境保存 SITE_ORIGIN 与 BACKEND_SSH_HOST、BACKEND_SSH_USER、BACKEND_SSH_KEY、BACKEND_SSH_KNOWN_HOSTS。不要把值写入文档、日志或 PR。旧 Worker 凭据不参与当前部署；仓库中的 Worker/wrangler 路径是历史方案。

部署只读取共享配置中的 Python 路径及 OCR 开关，不覆盖共享配置。普通回归关闭 OCR 和远程模型；启用 OCR 的候选版本还会安装依赖并执行真实 PNG 探针。

## 日常检查

以下命令在普通维护用户的 SSH 会话执行：

```sh
readlink -f ~/app/current
systemctl --user status hackathon-backend --no-pager
systemctl --user show hackathon-backend -p MemoryCurrent -p MemoryPeak -p MemoryHigh -p MemoryMax -p CPUQuotaPerSecUSec
curl --fail --silent --show-error http://127.0.0.1:18000/health
journalctl --user -u hackathon-backend -n 50 --no-pager
```

分享日志前先检查是否含单证内容、凭据或用户输入。不要通过打印 backend.env 排查配置。

从浏览器确认首页可用，并以 `?mock=0` 完成一次真实上传；默认示例模式不能证明 API 可用。可用已提交的合成样例，避免把未经授权的真实单证用于探针。完整步骤见[演示与验证](演示与验证.md)。

## 发布与回退

1. 通过 PR 审查和 CI 后合并；文档变更目前也会触发部署。
2. 部署只接受已有成功 push CI 的最新 main，旧提交不能覆盖线上。手动重跑也受此约束。
3. 候选版本先完成普通回归及启用时的 OCR 预检，随后切换 current，重启用户服务。
4. 公网探针验证首页、资源、API、文本 PDF，以及启用 OCR 时的 PNG 和扫描 PDF；响应传回执行器校验契约。
5. 验证失败触发回退，检查工作流结果、current 与健康接口，不能只看上传归档成功。

需要人工撤回当前发布时，先确认 current 的发布标识与该版本记录的前一版本；不要把任意历史目标标识当成命令参数：

```sh
# 将占位符替换为当前待撤回版本的发布标识
python3 ~/app/current/deploy/backend.py <当前发布标识> --rollback
```

脚本先停新服务，再恢复旧代码、依赖及服务配置，避免先降低内存限制导致仍运行的新模型被杀。**共享任务数据不回滚**。回退后重新检查页面和真实 API。没有有效前一版本时不能依赖自动回退，首次初始化须先准备可用基线。

## 数据与备份

任务与结果已接入 SQLite，终态结果继续导出 JSON 以兼容旧版本回退读取。启动时迁入旧 JSON，并将中断的任务标记为 FAILED / TASK_INTERRUPTED，不自动续跑。上线前仍须验证共享数据迁移与回退，详见 [SQLite 接入说明](../SQLITE_INTEGRATION.md)。

维护前选取无进行中任务的窗口，暂停新写入后备份共享 data，核对文件数量与可读性，保存到访问受限的独立位置；配置和部署密钥单独按秘密管理。保留备份与对应代码版本的关系，恢复先在隔离目录验证。不要用 data/init_db.py 或 seed_data.py 直接操作线上共享数据。

版本目录不会自动清理。确认当前版本、回退目标、备份与调查需要后再制定保留策略；不要在发布运行中清理候选目录或模型缓存。

## 资源与常见故障

| 现象 | 排查方向 |
|---|---|
| 首页正常、真实上传失败 | 确认真实模式；查 API 响应与任务 errors，HTTP 200 也可能表示 PARTIAL/FAILED |
| OCR 等待超过前端窗口 | 当前前端每 1.5 秒轮询、最多 60 次；不代表后端取消，保留任务 ID 查询结果 |
| 模型启动慢或下载失败 | 查用户服务日志、缓存可写性、网络和 Python 版本；不要靠另一个虚拟环境的手装依赖推断发布环境完整 |
| 内存异常或服务被终止 | 查 MemoryPeak 与日志，区分模型峰值、配额和主机总余量 |
| 源站健康而公网失败 | 分别排查 Nginx 路由、证书、Cloudflare 来源限制和边缘规则；避免为探针长期放开源站 |
| 长推理期间 SSH 中断 | 工作流已有 20 秒保活，继续检查连接与服务日志，不能把断连直接等同模型失败 |

服务单 worker，CPU 配额四核，MemoryHigh 6 GiB、MemoryMax 8 GiB。OCR 在线程内串行复用，推理线程数为 4；这不是全局任务限流。部署预检可能与旧服务同时占用模型内存，主机还需为系统与其他服务保留余量。当前没有正式并发容量结论，单样例耗时不能当 SLA。

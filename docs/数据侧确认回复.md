# 数据侧对契约待确认事项的回复

更新时间：2026-10-10

本文用于回复数据侧相关 issue，并明确第一版可以冻结的范围。本文只确认数据侧能够决定的内容；同步/轮询、HTTP 状态码等后端接口事项仍需后端确认。

## 一、第一版冻结结论

### 1. 第一版按单品名交付

第一版演示将每票货物限定为一个品名。当前 `comparisons[]` 按单品名结构实现，不新增复杂的多品名分组结构。

多品名列为已知限制，后续如扩展，需要增加商品身份或行项目关联，例如 `item_id`、文件内行号和跨文件商品匹配规则。第一版不根据 `line_no` 直接判断跨文件商品相同。

### 2. `field_key` 采用统一的 `snake_case` 命名

第一版后端 JSON、数据清洗结果、比对输入和数据库字段标识统一使用以下核心字段名：

| `field_key` | 中文名 | 类型 | 第一版用途 |
|---|---|---|---|
| `packages` | 包装件数 | `NUMBER` | 箱、托盘等包装数量 |
| `gross_weight` | 毛重 | `NUMBER` | 统一使用 `KGS` |
| `net_weight` | 净重 | `NUMBER` | 统一使用 `KGS` |
| `volume` | 体积 | `NUMBER` | 统一使用 `CBM` |
| `quantity` | 商品数量 | `NUMBER` | 统一使用 `PCS` 或原单据单位 |
| `hs_code` | HS 编码 | `CODE` | 保留字符串，避免丢失前导零 |
| `total_amount` | 总金额 | `MONEY` | 与 `currency` 配套使用 |
| `currency` | 币种 | `CODE` | 使用 ISO 4217 三位代码 |
| `description` | 货物描述 | `STRING` | 保留原文及归一值 |
| `invoice_no` | 发票号 | `STRING` | 用于单证关联 |
| `shipment_date` | 装运日期 | `DATE` | 使用 ISO 日期 |

单据标识和关联字段沿用以下命名：

```text
bill_of_lading_no
contract_no
container_no
shipper
consignee
port_of_loading
port_of_discharge
destination_country
```

这些字段可用于判断多份文件是否属于同一票货物，但第一版只将核心可比字段纳入差异页和统计口径。

后续新增字段必须先同步修改 `docs/数据契约.md` 和 `docs/schema/`，不得由后端单方面返回未定义字段。

### 3. `packages` 与 `quantity` 必须区分

- `packages` 表示包装件数，例如 `100 CARTON`。
- `quantity` 表示商品数量，例如 `2400 PCS`。
- “100 箱，每箱 24 个”应记录为 `packages = 100`、`quantity = 2400`。
- 如果单证没有提供每箱数量，系统不自行推算 `quantity`。
- 数值与单位分开保存，无法归一时 `normalized_value` 为 `null`，状态按契约标记为 `NORMALIZE_FAILED` 或其他适用状态。

## 二、单证类型与应有字段的最小规则表

下表是第一版用于区分 `NOT_IN_DOC` 和 `MISSING_IN_DOC` 的最小规则，不代表所有真实模板的完整字段清单。

| `field_key` | 商业发票 | 装箱单 | 提单 | 说明 |
|---|---|---|---|---|
| `description` | 必需 | 必需 | 必需 | 货物描述 |
| `packages` | 可选 | 必需 | 必需 | 包装件数 |
| `quantity` | 必需 | 必需 | 可选 | 商品数量；提单可能只给包装信息 |
| `gross_weight` | 可选 | 必需 | 必需 | 毛重 |
| `net_weight` | 可选 | 可选 | 可选 | 视模板和业务场景提供 |
| `volume` | 可选 | 可选 | 可选 | 有体积信息时抽取 |
| `hs_code` | 可选 | 可选 | 不适用 | 本第一版不要求提单提供 HS 编码 |
| `total_amount` | 必需 | 不适用 | 不适用 | 商业发票金额 |
| `currency` | 必需 | 不适用 | 不适用 | 与金额配套 |
| `invoice_no` | 必需 | 可选 | 不适用 | 发票号或关联号 |
| `shipment_date` | 可选 | 可选 | 可选 | 按文件实际提供情况抽取 |

定义如下：

- **必需**：在第一版选定场景中预期应出现；未抽取到时可标记 `MISSING_IN_DOC`。
- **可选**：可能出现，也可能没有；没有时不直接判定为缺失异常。
- **不适用**：第一版规则认为该类单证不承担该字段；标记 `NOT_IN_DOC`。

这张表先覆盖商业发票、装箱单、提单三类单证。扩展报关单、原产地证等类型时，再增加对应规则，不能默认套用上述三类规则。

## 三、对 issue 中 8 项数据侧问题的逐项回复

### 1. 一票货含多个品名时如何返回

第一版按单品名交付，当前 `comparisons[]` 保持现有单品名结构。多品名是已知限制，暂不阻塞第一版演示。

后续扩展时建议使用 `item_id + field_key` 作为比较键，并在抽取结果中保留文件内行号；但该结构需要 D、F、C 共同确认后再修改 Schema。

### 2. `field_key` 命名能否与数据库字段一致

可以。第一版采用契约第六节的 `snake_case` 核心字段清单。数据库可以使用通用的 `field_key` 列保存字段标识，也可以在业务表中使用同名列；无论采用哪种表结构，返回 JSON 的 `field_key` 必须保持上述命名。

### 3. 能否提供“单证类型 × 应有字段”规则表

可以。第一版先提供本文第二节的最小规则表，用于区分 `NOT_IN_DOC` 与 `MISSING_IN_DOC`。F 需要据此确认缺失和告警的触发逻辑；C 负责维护规则数据和样例。

### 4. `packages` 与 `quantity` 能否区分

可以。两者语义和单位分开保存，不因缺少包装换算信息而自行推算。具体单位归一失败时保留原文，并将标准值置为 `null`。

### 5. 成套单证样例

第一版优先提供商业发票、装箱单、提单的模拟或脱敏成套样例。每套至少覆盖：

- 一套字段一致的正常样例；
- 一套数量或重量冲突样例；
- 一套缺字段或无法识别样例。

样例应同时提供原始文件、解析后的预期字段和错误说明。真实公司名及真实单证只有在确认可用于演示后才使用。

### 6. 金标参考答案

数据侧负责整理金标初稿，包括字段值、状态、单位和来源页；D 负责人工核验展示需要的结果；F 负责确认比对结果和规则触发是否符合业务逻辑。

第一版先维护少量高质量样例，不以未经核验的大规模数据作为金标。金标集应记录版本号，例如 `golden-v1`。

### 7. 真实公司名与真实单证能否用于演示

第一版默认使用模拟或脱敏数据。若要使用真实公司名、真实单证或可识别的业务信息，需要由项目负责人确认使用权限；数据侧不自行作出授权判断。

### 8. 基础数据库进度与已建表结构

数据侧将按当前契约准备最小数据库结构，至少覆盖：

```text
tasks
documents
extracted_fields
hs_dictionary
golden_cases
```

第一版按单品名设计，不要求单独的 `items` 商品表。多品名扩展前，再共同确定商品身份和跨文件匹配结构。

## 四、仍需后端确认的事项

数据侧确认以上内容后，以下事项仍不属于 C 单方面可冻结的范围：

1. 上传后采用同步返回还是 `task_id` 轮询；
2. `PENDING`、`RUNNING`、`COMPLETED`、`PARTIAL`、`FAILED` 等任务状态是否按现有 Schema 返回；
3. `NOT_IN_DOC`、`MISSING_IN_DOC`、`NOT_CHECKED` 等状态是否由后端完整提供；
4. 失败是否始终使用非 2xx 状态码；
5. 第一版目的国规则覆盖范围；
6. 上传文件大小、数量和格式上限；
7. 是否提供 `bbox`、`confidence` 和人工修正接口。

因此，本文可以冻结**第一版数据侧字段和范围**，但不单独宣称整个前后端 API 契约已经完全冻结。

## 五、建议在 issue 中采用的简短结论

> 数据侧确认：第一版按单品名交付，当前 `comparisons[]` 维持单品名结构，多品名列为已知限制；`field_key` 采用契约第六节的 `snake_case` 核心字段清单；`packages` 与 `quantity` 分别表示包装件数和商品数量，不做无依据推算；先提供商业发票、装箱单、提单三类单证的最小“类型 × 应有字段”规则表，用于区分 `NOT_IN_DOC` 与 `MISSING_IN_DOC`。样例优先使用模拟或脱敏数据，金标由数据侧整理、D 人工核验、F 确认规则结果。同步/轮询、HTTP 失败码和任务状态等后端事项仍需后端确认。

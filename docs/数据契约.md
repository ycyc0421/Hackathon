# 数据契约 v0.1

前端（D）与后端（C/F）之间交换的数据格式。按 2026-10-12 main 实现修订；接口已接通，结构以 Schema 为准。

本文只覆盖 D 需要对接的部分：前端展示所需的数据、以及前端向后端提出的接口要求。抽取算法、数据库设计、合规规则内容不在本文范围内。

> **同一份约定的两种形式**：本文供人阅读；[`schema/`](schema/) 下是可机器校验的 JSON Schema，`npm run validate` 校验仓库示例；真实返回使用 `node backend/tools/validate_outputs.mjs <输出目录>` 校验。两者内容一致，以 schema 为准。

## 一、已定：两条设计规则

**规则 1 · 分两层**

- `extractions`：每个文件抽出了什么。保留原文，是"证据"。
- `comparisons`：同一字段跨文件比对，得出的结论。

仅保留一层不足以支撑展示：定位冲突时须能回答"该值抽取自何处"，分析错例时须能区分是抽取错误还是归一错误。

**规则 2 · 状态用枚举，且必须区分"不适用 / 没抽到 / 没查过"**

这三种都不是"没问题"，混成一个值或干脆不返回，页面就只能显示成通过。

## 二、已定：状态枚举取值

前端对每个值写条件分支。**字段名可以改，取值集合改起来成本高。**

### `task.status`

| 值 | 含义 |
|---|---|
| `PENDING` | 已创建未开始 |
| `PROCESSING` | 处理中 |
| `COMPLETED` | 处理完成（不代表没冲突） |
| `PARTIAL` | 部分成功：有文件失败，其余出了结果 |
| `FAILED` | 整体失败 |

`COMPLETED` 与 `PARTIAL` 必须分开，否则无法表达"有文件没处理成功"。

### `field.status`（该字段在某一份文件里的状态）

| 值 | 含义 |
|---|---|
| `EXTRACTED` | 正常抽出 |
| `LOW_CONFIDENCE` | 抽出来了但可信度低 |
| `NOT_IN_DOC` | 这份单证按规则本就没有这个字段（如提单没有成交金额） |
| `MISSING_IN_DOC` | 应该有的，文件里没找到 |
| `UNRECOGNIZED` | 定位到了但读不出值 |
| `NORMALIZE_FAILED` | 读出值了但无法归一（如"若干箱"） |

`NOT_IN_DOC` 与 `MISSING_IN_DOC` 必须分开，否则页面全是警告，用户会无视所有警告。

### `comparison.status`（跨文件比对结论）

| 值 | 含义 | 进问题清单 |
|---|---|---|
| `MATCH` | 参与比对的已识别值一致 | 含低可信取值时仍需复核 |
| `CONFLICT` | 有值且不一致 | 是 |
| `MISSING_IN_SOME` | 有的有值，有的该有没抽到 | 是 |
| `NOT_CHECKED` | 没规则覆盖或信息不足 | 是 |
| `UNRECOGNIZED` | 相关文件里都没识别出来 | 是 |
| `SINGLE_SOURCE` | 只有一份文件有该字段 | 否 |

`NOT_CHECKED` 必须返回。省略它等于让用户以为检查过了。

### `document.process_status`

`UPLOADED` / `PARSING` / `EXTRACTED` / `FAILED` / `UNSUPPORTED`

## 三、已定：前端对后端的三个要求

1. **请求错误返回非 2xx**，使用统一 `error` 对象。任务已创建后的处理失败，通过 2xx 响应中的任务状态与 `errors[]` 表达；HTTP 200 不等于核验成功。
2. **字段中文名由后端给**（`label`）。前端不维护 `field_key → 中文名` 映射，避免两边不一致。
3. **时间用 ISO 8601 带时区**，如 `2026-10-12T14:30:00+08:00`。

## 四、当前接口约定

| 事项 | 当前实现 |
|---|---|
| 创建任务 | 返回任务 ID 与当前状态，同一路径轮询；快速完成时带结果 |
| 文件输入 | PDF、图片；扫描件需启用 OCR；EDI 未实现 |
| 多品名 | 已支持商品目录、货号/描述对齐与逐商品比对；不可靠对齐显式降级 |
| 目的国 | US/DE/NL/FR/GB 演示规则，未经核实 |
| 置信度与坐标 | 当前后端返回 null，前端隐藏相关能力 |
| 人工修正、报告导出 | 没有实现接口；页面报告不等于可下载报告 |
| 评测 | 接口已实现，尚无正式评测时返回 NOT_RUN |
| 上传限制 | 最多 10 份，每份 20 MiB |
| 前端产物 | CI 构建 web/dist 并随整站版本发布，不提交构建产物 |

前端轮询间隔 1.5 秒、最多 60 次；耗时 OCR 可能超过该等待窗口，停止轮询不代表后端取消任务。待决策事项见[待确认问题](待确认问题.md)。不设未经确认的准确率门槛。

## 五、数据结构

### 一个检查任务

以下为省略数组的结构示意，不可作为完整响应校验：

```jsonc
{
  "task_id": "tsk_20261012_0001",
  "status": "COMPLETED",
  "created_at": "2026-10-12T14:30:00+08:00",
  "finished_at": "2026-10-12T14:30:18+08:00",
  "input": {
    "destination_country": "DE",
    "destination_country_name": "德国"
  },
  "items":      [ /* 见下 */ ],
  "documents":  [ /* 见下 */ ],
  "extractions":[ /* 见下 */ ],
  "comparisons":[ /* 见下 */ ],
  "risks":      [ /* 见下 */ ],
  "summary": {
    "document_count": 3, "field_count": 19,
    "conflict_count": 1, "missing_count": 0,
    "risk_count": 2, "unrecognized_count": 0
  },
  "errors": []
}
```

### `documents[]` — 文件清单

```json
{
  "file_id": "f2",
  "file_name": "装箱单-PL20261012.pdf",
  "file_type": "PDF",
  "doc_type": "PACKING_LIST",
  "process_status": "EXTRACTED",
  "page_count": 1,
  "error_message": null
}
```

`doc_type`：`COMMERCIAL_INVOICE` / `PACKING_LIST` / `BILL_OF_LADING` / `CUSTOMS_DECLARATION` / `CERTIFICATE_OF_ORIGIN` / `INSURANCE_POLICY` / `OTHER`。
判不出来给 `null`。

### `items[]` — 商品目录（任务内）

```json
{
  "item_id": "item_001",
  "display_name": "陶瓷马克杯",
  "description": "CERAMIC MUG 350ML WHITE",
  "line_no": 1
}
```

一票货可含多个商品，`items[]` 是**当前任务内**的商品目录。

- `item_id` 只是任务内的商品关联键：**不是类别、不是属性、不是 HS 编码、也不是正确答案**。跨任务可复用——`item_001` 在另一票货里就是另一个商品。
- 已支持多品名；单品名按票级字段处理时 `items[]` 可以为空。
- `display_name` 供前端直接展示；`line_no` 是该商品在原始文件中的行号，仅用于定位，不用于跨文件匹配。

**字段归属（`item_id`）**

- 商品级字段（`description`、`hs_code`、`quantity`、`packages`、`gross_weight`、`net_weight`、`volume`、`total_amount`、`currency`）的 `item_id` 指向 `items[]` 中的条目。
- 整票级字段（`invoice_no`、`shipment_date`、`shipper`、`consignee`、`port_of_loading`、`port_of_discharge`、`destination_country`、`container_no`、`bill_of_lading_no`、`contract_no` 等）`item_id` 为 `null`。
- `packages` / `gross_weight` / `net_weight` / `volume` 只有整票汇总值时 `item_id` 给 `null`，不要把总值复制到每个商品。
- `comparisons[]` 的比较键是 `item_id + field_key`：同一字段按商品分别比对，整票级字段跨文件只比一次。
- `line_no`（`Item` 与 `Field` 上的）只表示某份文件中的原始行号，不是跨文件身份，不用于跨文件匹配。

### `extractions[].fields[]` — 单字段（第 1 层）

```json
{
  "field_key": "packages",
  "label": "件数",
  "raw_text": "TOTAL: SAY ONE HUNDRED AND TWENTY (120) CARTONS ONLY",
  "raw_value": "120 CARTONS",
  "normalized_value": 120,
  "unit": "CARTON",
  "confidence": null,
  "status": "EXTRACTED",
  "item_id": "item_001",
  "line_no": 1,
  "page": 1,
  "bbox": null,
  "bbox_unit": null
}
```

- `raw_text` 原样保留，不清洗
- `normalized_value` 归一失败给 `null`，类型见第六节的 `value_type`
- `item_id` 标记该字段归属的商品，整票级字段为 `null`，归属规则见上面的 `items[]` 一节

### `comparisons[]` — 跨文件比对（第 2 层）

```json
{
  "comparison_id": "cmp_1",
  "field_key": "packages",
  "item_id": "item_001",
  "label": "件数",
  "value_type": "NUMBER",
  "unit": "CARTON",
  "status": "CONFLICT",
  "canonical_value": null,
  "severity": "ERROR",
  "rule_id": "CROSS_CHECK_001",
  "note": null,
  "suggested_action": "核对发票与装箱单的件数来源，确认后更正不一致的单证",
  "values": [
    {"file_id":"f1","file_name":"商业发票-INV20261012.pdf","raw_value":"100 CARTONS","normalized_value":100,"field_status":"LOW_CONFIDENCE","page":1,"bbox":[80,506,260,22]},
    {"file_id":"f2","file_name":"装箱单-PL20261012.pdf","raw_value":"120 CARTONS","normalized_value":120,"field_status":"EXTRACTED","page":1,"bbox":[180,420,240,24]}
  ]
}
```

- `canonical_value` **必须为 `null`**。系统不判断谁对。
- `item_id` 标记该条比对归属的商品，整票级比对为 `null`；比较键为 `item_id + field_key`。
- `severity`：`INFO` / `WARNING` / `ERROR`，决定页面配色。
- `values[].field_status` 用 `field.status` 那套枚举，这样一行里能同时表达"这份是 120"和"那份没找到"。
- `values[].item_id` 可选，用于追溯该值归属的商品；与所属比对条目的 `item_id` 一致。
- `suggested_action` 可选，发现该问题后的处理建议，由后端/规则侧给出。`null` 或缺省表示没有可靠建议，前端不显示该区块。后端只指出差异、不指定哪份文件正确，建议不得代替结论。

### `risks[]` — 合规与归类风险

```json
{
  "risk_id": "rsk_1",
  "type": "MISSING_CERTIFICATE",
  "severity": "WARNING",
  "title": "演示规则·未经核实：原产地证明核对提示",
  "detail": "仅示意风险结构；规则适用性和依据尚未核实，不构成申报要求。",
  "related_field_keys": ["hs_code"],
  "related_file_ids": [],
  "destination_country": "DE",
  "rule_id": "DE-IMP-004",
  "rule_source": "演示规则·未经核实",
  "suggested_action": null
}
```

`type`：`MISSING_CERTIFICATE` / `HS_CLASSIFICATION` / `RULE_UNCOVERED` / `OTHER`。

`rule_id` 为 `null` 时，页面显示为**"模型建议，未经规则校验"**，与规则命中的风险分组显示。不允许凭空提示"必须有 X 证书"。

`suggested_action` 可选，发现该风险后的处理建议。`null` 或缺省时不显示。合规风险提示同样不代替结论：未经核实的合规规则不给确定的申报指令。

第一版目的国规则覆盖 **美国（US）、德国（DE）、荷兰（NL）、法国（FR）、英国（GB）**，均为**演示规则·未经核实，不作为正式合规结论**。

### `errors[]`

```json
{"code": "DOC_PARSE_FAILED", "message": "图像分辨率过低，无法识别版式", "level": "ERROR", "file_ids": ["f3"]}
```

`code` 英文稳定（前端做特殊处理），`message` 中文（直接展示）。`level`：`FATAL` / `ERROR` / `WARNING`。

### `Evaluation` — 评测结果

```json
{
  "status": "NOT_RUN",
  "dataset_version": null,
  "sample_count": 0,
  "model_version": null,
  "metrics": null,
  "run_at": null
}
```

`status`：`NOT_RUN` / `RUNNING` / `DONE` / `FAILED`。

设计上就支持"尚未评测"，避免看板被迫填假数字。

## 六、`field_key` 字段清单

`value_type` 决定前端渲染：`MONEY` 拆币种显示，`CODE` 用等宽字体，`DATE` 格式化。

### 核心可比字段

| `field_key` | 中文 | `value_type` | 归一单位 |
|---|---|---|---|
| `packages` | 件数 | `NUMBER` | `CARTON` |
| `gross_weight` | 毛重 | `NUMBER` | `KGS` |
| `net_weight` | 净重 | `NUMBER` | `KGS` |
| `volume` | 体积 | `NUMBER` | `CBM` |
| `quantity` | 数量 | `NUMBER` | `PCS` |
| `hs_code` | HS 编码 | `CODE` | — |
| `total_amount` | 总金额 | `MONEY` | — |
| `currency` | 币种 | `CODE` | — |
| `description` | 货物描述 | `STRING` | — |
| `invoice_no` | 发票号 | `STRING` | — |
| `shipment_date` | 装运日期 | `DATE` | — |

### 单据标识

`bill_of_lading_no` 提单号、`contract_no` 合同号、`container_no` 集装箱号、`shipper` 发货人、`consignee` 收货人、`port_of_loading` 起运港、`port_of_discharge` 目的港、`destination_country` 目的国

这些是判断"几份文件是不是同一票货"的依据。

### 已确认：`packages` 与 `quantity` 必须区分（数据侧）

- `packages` 表示包装件数（如 `100 CARTON`）；`quantity` 表示商品数量（如 `2400 PCS`）。
- "100 箱，每箱 24 个"记为 `packages = 100`、`quantity = 2400`。
- 单证未给每箱数量时**不自行推算** `quantity`；无法归一时 `normalized_value` 为 `null`，按 `NORMALIZE_FAILED` 等适用状态标记。

### 已确认：单证类型 × 应有字段最小规则表（数据侧）

第一版用于区分 `NOT_IN_DOC` 与 `MISSING_IN_DOC` 的最小规则，覆盖商业发票、装箱单、提单三类，不代表真实模板的完整字段清单。扩展报关单、原产地证等类型时另增规则，不默认套用本表。

| `field_key` | 商业发票 | 装箱单 | 提单 |
|---|---|---|---|
| `description` | 必需 | 必需 | 必需 |
| `packages` | 可选 | 必需 | 必需 |
| `quantity` | 必需 | 必需 | 可选 |
| `gross_weight` | 可选 | 必需 | 必需 |
| `net_weight` | 可选 | 可选 | 可选 |
| `volume` | 可选 | 可选 | 可选 |
| `hs_code` | 可选 | 可选 | 不适用 |
| `total_amount` | 必需 | 不适用 | 不适用 |
| `currency` | 必需 | 不适用 | 不适用 |
| `invoice_no` | 必需 | 可选 | 不适用 |
| `shipment_date` | 可选 | 可选 | 可选 |

- **必需**：预期应出现，未抽到时可标记 `MISSING_IN_DOC`。
- **可选**：可有可没有，没有时不直接判缺失异常。
- **不适用**：该类单证不承担该字段，标记 `NOT_IN_DOC`。

### 多品名与内部模型

商品目录、字段和比对的 item_id 已落地；比较键为 item_id + field_key。按货号、其次描述对齐，不能按行号猜测身份。无法可靠对齐时返回 NOT_CHECKED 并解释原因。

内部模型的 line_items、alignment_status、summary.item_count、风险的 related_item_ids 不属于当前公开 Schema，由 backend/app/frontend_view.py 映射或剔除。公开商品名是 display_name，不直接透传内部 label。

### 已确认：样例与金标（数据侧）

- **样例**：优先提供商业发票、装箱单、提单的模拟或脱敏成套样例，覆盖"字段一致正常 / 数量重量冲突 / 缺字段或无法识别"三类，并附原始文件、预期字段与错误说明。真实公司名与真实单证须经项目负责人确认后才用于演示。
- **金标**：数据侧整理初稿（字段值、状态、单位、来源页），前端人工核验展示结果，后端确认比对与规则触发的业务逻辑。先维护少量高质量样例，记录版本号（如 `golden-v1`）。
- **数据库**：独立 SQLite 数据工具已落地；线上 main 仍使用 JSON 任务存储，数据库接入尚待合并。数据工具包含 `tasks`、`items`、`documents`、`extracted_fields`、`comparisons`、`risks`、`hs_dictionary`、`golden_cases` 等表；API 契约中的 `items[]` 在数据库中以任务内商品表保存，`item_id` 仍只在任务范围内有意义。

## 七、接口

```
POST   /api/v1/checks                      创建任务，multipart 上传
GET    /api/v1/checks/{task_id}            查状态与结果（轮询用同一个）
GET    /api/v1/evaluation/latest           评测状态与结果
```

`GET /checks/{id}` 一个接口同时用于轮询和取最终结果，靠 `status` 区分，不拆两个。

统一错误：

```json
{"error": {"code": "FILE_TOO_LARGE", "message": "文件超过大小限制"}}
```

HTTP：`400` 参数错 / `404` 任务不存在 / `413` 文件过大或过多 / `500` 服务端错误。文件解析失败通常写入任务 errors，任务为 PARTIAL 或 FAILED。人工修正与报告导出接口尚未实现。

## 九、命名约定

- 字段名 `snake_case`
- 枚举值 `SCREAMING_SNAKE_CASE`
- 缺失值用 `null`，**不用空字符串**（空字符串分不清"没抽到"和"抽到了但是空的"）
- `normalized_value` 仅允许字符串、数字、布尔值或 null，不能放对象。金额用数值，币种通过 currency 字段及适用的 unit 表达；MONEY 不改变该类型约束。

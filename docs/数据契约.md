# 数据契约 v0.1

前端（D）与后端（C/F）之间交换的数据格式。**D 起草，数据侧字段与范围已经数据侧确认；后端接口事项仍待后端确认。**

本文只覆盖 D 需要对接的部分：前端展示所需的数据、以及前端向后端提出的接口要求。抽取算法、数据库设计、合规规则内容不在本文范围内。

> **同一份约定的两种形式**：本文供人阅读；[`schema/`](../schema/) 下是可机器校验的 JSON Schema，`npm run validate` 可验证真实返回是否符合契约。两者内容一致，以 schema 为准。

---

## 一、已定：两条设计规则

**规则 1 · 分两层**

- `extractions`：每个文件抽出了什么。保留原文，是"证据"。
- `comparisons`：同一字段跨文件比对，得出的结论。

仅保留一层不足以支撑展示：定位冲突时须能回答"该值抽取自何处"，分析错例时须能区分是抽取错误还是归一错误。

**规则 2 · 状态用枚举，且必须区分"不适用 / 没抽到 / 没查过"**

这三种都不是"没问题"，混成一个值或干脆不返回，页面就只能显示成通过。

## 二、已定：状态枚举取值

前端对每个值写条件分支。**字段名可以改，取值集合改起来成本高。**

### `task.status`

| 值 | 含义 |
|---|---|
| `PENDING` | 已创建未开始 |
| `RUNNING` | 处理中 |
| `COMPLETED` | 处理完成（不代表没冲突） |
| `PARTIAL` | 部分成功：有文件失败，其余出了结果 |
| `FAILED` | 整体失败 |

`COMPLETED` 与 `PARTIAL` 必须分开，否则无法表达"有文件没处理成功"。

### `field.status`（该字段在某一份文件里的状态）

| 值 | 含义 |
|---|---|
| `EXTRACTED` | 正常抽出 |
| `LOW_CONFIDENCE` | 抽出来了但可信度低 |
| `NOT_IN_DOC` | 这份单证按规则本就没有这个字段（如提单没有成交金额） |
| `MISSING_IN_DOC` | 应该有的，文件里没找到 |
| `UNRECOGNIZED` | 定位到了但读不出值 |
| `NORMALIZE_FAILED` | 读出值了但无法归一（如"若干箱"） |

`NOT_IN_DOC` 与 `MISSING_IN_DOC` 必须分开，否则页面全是警告，用户会无视所有警告。

### `comparison.status`（跨文件比对结论）

| 值 | 含义 | 进问题清单 |
|---|---|---|
| `MATCH` | 有值的文件都一致 | 否 |
| `CONFLICT` | 有值且不一致 | 是 |
| `MISSING_IN_SOME` | 有的有值，有的该有没抽到 | 是 |
| `NOT_CHECKED` | 没规则覆盖或信息不足 | 是 |
| `UNRECOGNIZED` | 相关文件里都没识别出来 | 是 |
| `SINGLE_SOURCE` | 只有一份文件有该字段 | 否 |

`NOT_CHECKED` 必须返回。省略它等于让用户以为检查过了。

### `document.process_status`

`UPLOADED` / `PARSING` / `EXTRACTED` / `FAILED` / `UNSUPPORTED`

## 三、已定：前端对后端的三个要求

1. **失败返回非 2xx**，不要用 200 包 `success: false`。否则前端会把失败渲染成"检查完成，没有问题"。
2. **字段中文名由后端给**（`label`）。前端不维护 `field_key → 中文名` 映射，避免两边不一致。
3. **时间用 ISO 8601 带时区**，如 `2026-10-12T14:30:00+08:00`。

## 五、数据结构

### 一个检查任务

```json
{
  "task_id": "tsk_20261012_0001",
  "status": "COMPLETED",
  "created_at": "2026-10-12T14:30:00+08:00",
  "finished_at": "2026-10-12T14:30:18+08:00",
  "input": {
    "destination_country": "DE",
    "destination_country_name": "德国"
  },
  "documents":  [ /* 见下 */ ],
  "extractions":[ /* 见下 */ ],
  "comparisons":[ /* 见下 */ ],
  "risks":      [ /* 见下 */ ],
  "summary": {
    "document_count": 3, "field_count": 19,
    "conflict_count": 1, "missing_count": 0,
    "risk_count": 2, "unrecognized_count": 0
  },
  "errors": []
}
```

### `documents[]` — 文件清单

```json
{
  "file_id": "f2",
  "file_name": "装箱单-PL20261012.pdf",
  "file_type": "PDF",
  "doc_type": "PACKING_LIST",
  "process_status": "EXTRACTED",
  "page_count": 1,
  "error_message": null
}
```

`doc_type`：`COMMERCIAL_INVOICE` / `PACKING_LIST` / `BILL_OF_LADING` / `CUSTOMS_DECLARATION` / `CERTIFICATE_OF_ORIGIN` / `INSURANCE_POLICY` / `OTHER`。
判不出来给 `null`。

### `extractions[].fields[]` — 单字段（第 1 层）

```json
{
  "field_key": "packages",
  "label": "件数",
  "raw_text": "TOTAL: SAY ONE HUNDRED AND TWENTY (120) CARTONS ONLY",
  "raw_value": "120 CARTONS",
  "normalized_value": 120,
  "unit": "CARTON",
  "confidence": 0.96,
  "status": "EXTRACTED",
  "page": 1,
  "bbox": [180, 420, 240, 24],
  "bbox_unit": "PX"
}
```

- `raw_text` 原样保留，不清洗
- `normalized_value` 归一失败给 `null`，类型见第六节的 `value_type`
- 第一版按单品名组织；多品名扩展为已知限制，见第六节

### `comparisons[]` — 跨文件比对（第 2 层）

```json
{
  "comparison_id": "cmp_1",
  "field_key": "packages",
  "label": "件数",
  "value_type": "NUMBER",
  "unit": "CARTON",
  "status": "CONFLICT",
  "canonical_value": null,
  "severity": "ERROR",
  "rule_id": "CROSS_CHECK_001",
  "note": null,
  "values": [
    {"file_id":"f1","file_name":"商业发票-INV20261012.pdf","raw_value":"100 CARTONS","normalized_value":100,"field_status":"LOW_CONFIDENCE","page":1,"bbox":[80,506,260,22]},
    {"file_id":"f2","file_name":"装箱单-PL20261012.pdf","raw_value":"120 CARTONS","normalized_value":120,"field_status":"EXTRACTED","page":1,"bbox":[180,420,240,24]}
  ]
}
```

- `canonical_value` **默认 `null`**。系统不判断谁对。
- `severity`：`INFO` / `WARNING` / `ERROR`，决定页面配色。
- `values[].field_status` 用 `field.status` 那套枚举，这样一行里能同时表达"这份是 120"和"那份没找到"。

### `risks[]` — 合规与归类风险

```json
{
  "risk_id": "rsk_1",
  "type": "MISSING_CERTIFICATE",
  "severity": "WARNING",
  "title": "目的国为德国，未在本票文件中找到原产地证明",
  "detail": "依据规则 DE-IMP-004：……",
  "related_field_keys": ["hs_code"],
  "related_file_ids": [],
  "destination_country": "DE",
  "rule_id": "DE-IMP-004",
  "rule_source": "团队配置的目的国规则集 v1"
}
```

`type`：`MISSING_CERTIFICATE` / `HS_CLASSIFICATION` / `RULE_UNCOVERED` / `OTHER`。

`rule_id` 为 `null` 时，页面显示为**"模型建议，未经规则校验"**，与规则命中的风险分组显示。不允许凭空提示"必须有 X 证书"。

### `errors[]`

```json
{"code": "DOC_PARSE_FAILED", "message": "图像分辨率过低，无法识别版式", "level": "ERROR", "file_ids": ["f3"]}
```

`code` 英文稳定（前端做特殊处理），`message` 中文（直接展示）。`level`：`FATAL` / `ERROR` / `WARNING`。

### `Evaluation` — 评测结果

```json
{
  "status": "NOT_RUN",
  "dataset_version": null,
  "sample_count": 0,
  "model_version": null,
  "metrics": null,
  "run_at": null
}
```

`status`：`NOT_RUN` / `RUNNING` / `DONE` / `FAILED`。

设计上就支持"尚未评测"，避免看板被迫填假数字。

## 六、`field_key` 字段清单

`value_type` 决定前端渲染：`MONEY` 拆币种显示，`CODE` 用等宽字体，`DATE` 格式化。

### 核心可比字段

| `field_key` | 中文 | `value_type` | 归一单位 |
|---|---|---|---|
| `packages` | 件数 | `NUMBER` | `CARTON` |
| `gross_weight` | 毛重 | `NUMBER` | `KGS` |
| `net_weight` | 净重 | `NUMBER` | `KGS` |
| `volume` | 体积 | `NUMBER` | `CBM` |
| `quantity` | 数量 | `NUMBER` | `PCS` |
| `hs_code` | HS 编码 | `CODE` | — |
| `total_amount` | 总金额 | `MONEY` | — |
| `currency` | 币种 | `CODE` | — |
| `description` | 货物描述 | `STRING` | — |
| `invoice_no` | 发票号 | `STRING` | — |
| `shipment_date` | 装运日期 | `DATE` | — |

### 单据标识

`bill_of_lading_no` 提单号、`contract_no` 合同号、`container_no` 集装箱号、`shipper` 发货人、`consignee` 收货人、`port_of_loading` 起运港、`port_of_discharge` 目的港、`destination_country` 目的国

这些是判断"几份文件是不是同一票货"的依据。

### 最小可用集合

时间紧就做这 6 个：`packages`、`gross_weight`、`hs_code`、`total_amount`、`currency`、`description`。

够演全部五种状态：一致、冲突、缺字段、未识别、无法比对。

### 已确认：`packages` 与 `quantity` 必须区分（数据侧）

- `packages` 表示包装件数（如 `100 CARTON`）；`quantity` 表示商品数量（如 `2400 PCS`）。
- "100 箱，每箱 24 个"记为 `packages = 100`、`quantity = 2400`。
- 单证未给每箱数量时**不自行推算** `quantity`；无法归一时 `normalized_value` 为 `null`，按 `NORMALIZE_FAILED` 等适用状态标记。

### 已确认：单证类型 × 应有字段最小规则表（数据侧）

第一版用于区分 `NOT_IN_DOC` 与 `MISSING_IN_DOC` 的最小规则，覆盖商业发票、装箱单、提单三类，不代表真实模板的完整字段清单。扩展报关单、原产地证等类型时另增规则，不默认套用本表。

| `field_key` | 商业发票 | 装箱单 | 提单 |
|---|---|---|---|
| `description` | 必需 | 必需 | 必需 |
| `packages` | 可选 | 必需 | 必需 |
| `quantity` | 必需 | 必需 | 可选 |
| `gross_weight` | 可选 | 必需 | 必需 |
| `net_weight` | 可选 | 可选 | 可选 |
| `volume` | 可选 | 可选 | 可选 |
| `hs_code` | 可选 | 可选 | 不适用 |
| `total_amount` | 必需 | 不适用 | 不适用 |
| `currency` | 必需 | 不适用 | 不适用 |
| `invoice_no` | 必需 | 可选 | 不适用 |
| `shipment_date` | 可选 | 可选 | 可选 |

- **必需**：预期应出现，未抽到时可标记 `MISSING_IN_DOC`。
- **可选**：可有可没有，没有时不直接判缺失异常。
- **不适用**：该类单证不承担该字段，标记 `NOT_IN_DOC`。

### 已确认：第一版按单品名交付（数据侧）

第一版每票货物限定一个品名，`comparisons[]` 保持现有单品名结构，不新增多品名分组。多品名列为**已知限制**；后续扩展需引入商品身份或行项目关联（如 `item_id + field_key` 作比较键，并保留文件内行号），由前端、后端、数据侧共同确认后再改 Schema。第一版不按 `line_no` 直接判断跨文件商品相同。

### 已确认：样例与金标（数据侧）

- **样例**：优先提供商业发票、装箱单、提单的模拟或脱敏成套样例，覆盖"字段一致正常 / 数量重量冲突 / 缺字段或无法识别"三类，并附原始文件、预期字段与错误说明。真实公司名与真实单证须经项目负责人确认后才用于演示。
- **金标**：数据侧整理初稿（字段值、状态、单位、来源页），前端人工核验展示结果，后端确认比对与规则触发的业务逻辑。先维护少量高质量样例，记录版本号（如 `golden-v1`）。
- **数据库**：按最小结构覆盖 `tasks`、`documents`、`extracted_fields`、`hs_dictionary`、`golden_cases`；第一版单品名设计，不单设 `items` 商品表。

## 七、接口

```
POST   /api/v1/checks                      创建任务，multipart 上传
GET    /api/v1/checks/{task_id}            查状态与结果（轮询用同一个）
PATCH  /api/v1/checks/{task_id}/fields/... 人工修正（第 8 项未定，暂不做）
GET    /api/v1/checks/{task_id}/report     报告导出（第 9 项未定）
GET    /api/v1/evaluation/latest           评测结果（第 10 项未定）
```

`GET /checks/{id}` 一个接口同时用于轮询和取最终结果，靠 `status` 区分，不拆两个。

统一错误：

```json
{"error": {"code": "FILE_TOO_LARGE", "message": "文件超过大小限制"}}
```

HTTP：`400` 参数错 / `404` 任务不存在 / `413` 文件过大 / `422` 无法解析 / `500` 服务端错误。

## 九、命名约定

- 字段名 `snake_case`
- 枚举值 `SCREAMING_SNAKE_CASE`
- 缺失值用 `null`，**不用空字符串**（空字符串分不清"没抽到"和"抽到了但是空的"）
- 金额 `{"value": 12500.00, "currency": "USD"}`，货币符号不进数字
